# Entity model & wiki architecture

Landscape check against prior art, starting from the canonical source: Karpathy's [LLM Wiki pattern](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
and [langchain-ai/openwiki](https://github.com/langchain-ai/openwiki).

## Three layers (Karpathy's model, applied to "all repos" instead of "one repo's content")

1. **Raw sources** — `~/dev/*`, `~/infra/*` git repos, plus non-git config dirs
   (`~/.claude`, `~/.config/opencode`, `~/.pi`). Immutable, atlas only reads.
2. **The wiki** — `~/wiki/atlas/` — generated markdown. OKF entity pages +
   `index.md` (catalog, updated every scan) + `log.md` (append-only,
   `## [date] scan | N repos` format, grep-able).
3. **The schema** — this repo (`atlas`) + `~/wiki/AGENTS.md`. Tells the agent
   the conventions; co-evolves as we learn what works.

## Four systems, four jobs (verified against the running wiring)

| System | Question it answers | Output | Owner |
|---|---|---|---|
| **GitNexus** | "What breaks if I change X?" (code call graph, blast radius) | `.gitnexus/` index; on-demand MCP facts (`query`/`context`/`impact`/`trace`/`cypher`) | GitNexus CLI/MCP, per-repo |
| **OpenWiki** | "What does this repo do, narratively?" (architecture/domain/decisions) | `openwiki/` per repo, with its own frontmatter | OpenWiki, LLM via `openwiki-llm-env.sh` |
| **repo-atlas.sh** | "What repos/configs/services exist on this machine?" (OKF entity index) | `~/wiki/atlas/`, one entity doc per repo/config/service | Atlas scanner (`scripts/repo-atlas.sh`, `service-atlas.sh`), no LLM |
| **CodeAlmanac** | "What durable decisions/pitfalls came out of transcripts?" | `almanac/` per repo | CodeAlmanac, its own launchd sync/garden jobs |

These are **different outputs with different owners**. OpenWiki's frontmatter lives
in each repo's `openwiki/`; repo-atlas's OKF entities live in `~/wiki/atlas/`. The
latter is the machine-wide entity index and is the only one that the entity model
below governs. OpenWiki does **not** replace `repo-atlas.sh`; they run side by side.
GitNexus is the code graph; `gitnexus wiki` is not Atlas's narrative path, and no
second graph layer is built.

## The OKF entity model (repo-atlas.sh output)

| Realm (`type:`) | Examples | Source of truth |
|---|---|---|
| `repo` | repos under ~/dev | `.git` scan |
| `agent-harness` | claude-code, opencode, pi | fixed config dirs |
| `service` | launchd jobs, litellm proxy | launchctl + listening ports |
| `job` | GitHub Actions cron, VPS systemd timers + cron, dagster schedules, brew services, containers with a restart policy | no scanner shipped; write `jobs/<name>.md` by hand or with your own script |

`service` and `job` do not overlap by construction: `service-atlas.sh` owns
`~/Library/LaunchAgents`; `job` covers everything scheduled that is not a local
plist. Both record a declaration *and* a last observed outcome,
because a schedule that exists is not a schedule that ran.

Relations: `part-of`, `depends-on`, `used-by`, `source` — plain `[[slug]]` links.
Entity frontmatter (generated by `repo-atlas.sh`): `type/title/path/remote/category/
stack/last-commit/branch/dirty/unpushed/gitnexus-indexed/ktx/timestamp/
manual-reviewed/manual-hash`. `gitnexus-indexed: yes/no` records GitNexus presence;
GitNexus itself stays on-demand, so no persisted call-graph facts exist.

## Recursion boundary

Atlas's generated output never feeds back into generation:

- `.openwikiignore` (seeded by `atlas onboard`) excludes `openwiki/`, `almanac/`,
  `.gitnexus/`, build artifacts, lockfiles, and `.env*` from the OpenWiki scan.
- Generated outputs are not source docs and are never auto-committed. The cascade
  only writes local files; a human reviews and commits generated docs.
- Refresh triggers are source commits (post-commit hook, background) plus the
  launchd weekly scans. GitHub Actions is not the canonical refresh: the cloud
  workflow OpenWiki scaffolds is deleted every cascade run.

## LLM routing for OpenWiki (resolved, per scripts/openwiki-llm-env.sh)

Narrative generation routes by **repo visibility first**, proxy health second:

- **Public repo, proxy up** → `$ATLAS_MODEL_PUBLIC` (default `atlas-public`) via
  the LiteLLM proxy at `$ATLAS_LLM_URL` (default `http://localhost:4000`).
- **Public repo, proxy down** → the optional `ATLAS_FALLBACK_URL/_KEY/_MODEL`
  endpoint when all three are set; otherwise generation is refused.
- **Private/unknown repo, proxy up** → `$ATLAS_MODEL_PRIVATE` (default
  `atlas-private`) via the same proxy. Point it at a local model.
- **Private/unknown repo, proxy down** → generation **refused** (logged to
  `~/wiki/atlas/fallback.log` + macOS notification). No cloud path for private code.
- Configure no global fallback in the proxy for the private model group, or a
  proxy-side fallback can still send private code to the cloud.

The script is the source of truth.
